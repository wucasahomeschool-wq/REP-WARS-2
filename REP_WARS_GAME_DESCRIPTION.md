## Authority boundary

- **Authoritative gameplay** lives in **TypeScript** under `src/`.
- **Unity** (`Unity/Assets/RepWars/`) is presentation and input: HTTP commands,
  map rendering, workout UI, play loop. It does not own GameState.
- **Authored worlds** load from `worlds/` via `WorldCatalog` / `WorldDefinition`.
  Production maps are **not** generated by `MapEngine` at runtime.

## Single source of truth

- **`GameState`** (`src/types/GameState.ts`) is the one authoritative runtime
  world. Schema version **13** (`GAME_STATE_SCHEMA_VERSION`).
- Engines (Battle, WorldSimulator/events, DecisionEngine) read narrow views and
  return results; the **Orchestrator** applies mutations.
- Machine-readable commands: **`src/orchestration/commandIndex.ts`** (32 entries:
  30 implemented, 2 unsupported).

## Persistence

- **Supabase** (when `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` are set):
  `player_worlds` (one row per `playerId`, CAS `state_version`), `workout_history`,
  atomic RPC `commit_authoritative_player_world` (world + history in one transaction).
- **In-memory** stores when env vars are unset (dev default; state lost on exit).
- Migrations live in `supabase/migrations/`; do not edit pushed migrations casually.

## HTTP development server

- `src/server/main.ts` — `node:http` on `127.0.0.1`, port **8787** (or `PORT`).
- **Allowlist only** (`src/server/allowlist.ts`): player-facing commands; notably
  **not** exposed: `ADVANCE_WORLD`, `AI_DECIDE`, `RESOLVE_COMMITMENT`.
- Mutating commands persist after `Orchestrator.execute`; clients **GET_GAME_STATE**
  afterward (responses do not embed full state).
- Per-player command queue; Supabase path uses atomic commit with buffered workout
  history on the same RPC.

## Time and continuous world (current behavior)

- **Simulation clock:** integer **`worldTick`** on GameState. Prototype mapping:
  **1 world tick ≈ 1 minute** (`WORLD_TICK_DURATION_MS = 60_000`, economy config).
- **World advance:** `ADVANCE_WORLD` runs `ContinuousWorldEngine` (AI commitments,
  army movement, events, invasions, economy pass). Chunk cap **64 ticks** per call.
- **Catch-up:** `SYNC_PLAYER_WORLD` repeats `ADVANCE_WORLD` in chunks toward
  `targetWorldTick`, gated by **`WorldTimeAuthority`**. Dev HTTP session uses
  **`FixedWorldTimeAuthority(0)`** — catch-up to tick 0 only unless tests inject
  another authority.
- **Wall clock foundation:** `lastProcessedAtMs` on GameState +
  `advanceAuthoritativeWorldClock()` (`src/world/realtimeClock.ts`) convert UTC
  elapsed time to whole ticks. **Persisted and tested; not wired into the HTTP
  session or auto-advance on each request.** Next phase: scheduler consuming
  elapsed ticks without running unbounded sim in one request.
- **Event engine** still uses **`turn`** on GameState; adapter
  `ticksPerEventTurn = 1` (one world tick → one event turn step).

## Map and visibility (current vs product)

- **Current production world:** entire current authored world is **visible** to the
  player faction. There is **no territory fog** on GameState. Polygons live on
  **WorldDefinition**, not on GameState.
- **Legacy:** `MapEngine` / `MapWorldState` / scout-fog (`src/map/`) — hex demo and
  tests only; documented as non-production.

## Playable loop today

- **Level 1** authored tutorial world with beat controller (`level1Tutorial`).
- **Workouts:** purposes `NORMAL_TROOPS`, `EXTRA_CONSTRUCTION_WORKERS`,
  `GOLDEN_YIELD`, `DEFENSE` — session commands + `FINALIZE_WORKOUT` reward pipeline.
- **Combat:** `ATTACK` (immediate battle, staging march, or **invasion** vs player
  with defense workout window). **BattleEngine** resolves battles.
- **Economy:** territory accrual, `COLLECT_RESOURCES`, timed **construction**
  (CITY, FORTIFICATION, FARM, MINE, LUMBER), food consumption on world advance
  (Level 1 gated where applicable).
- **AI:** DecisionEngine + **commitments**; simulation during `ADVANCE_WORLD` /
  `SYNC_PLAYER_WORLD`. No **AI Director** in repo.
- **Unity Game Interface V1:** map, workout screen, attack, construction entry,
  `RepWarsApiClient` → HTTP bridge.

## Prototype vs product tensions (do not hide)

- **Banked Troops** (`playerRewards.bankedTroops`) exist; player `ATTACK` can commit
  banked troops. Long-term product doc prefers workout-gated actions over large
  spendable banks — current code is still prototype-aligned with troops workouts.
- **OFFER_PEACE** and **TRADE** are catalogued but **unsupported**
  (`FEATURE_NOT_IMPLEMENTED`).
- **Scout / explore / claim / recruit / split army** — product concepts; **no**
  matching player commands in `COMMAND_INDEX` today.

================================================================================
1. GAME OVERVIEW
================================================================================

Rep Wars is a mobile-first fitness strategy game where real-world workouts
enable military actions, conquest, and empire management.

**Intended** core loop:

    STRATEGIC DECISION
        ↓
    REQUIRED WORKOUT
        ↓
    ACTION COMPLETES
        ↓
    GAME CONSEQUENCE
        ↓
    NEXT DECISION

**Current prototype** also supports immediate map commands (e.g. MOVE, REINFORCE)
and troop workouts that bank or commit troops; invasion defense is workout-gated.

The game is intended to be a persistent, AI-driven world with territorial
conquest, armies, cities, resources, diplomacy, exploration, fog of war, and
world events. Many of these are partial or legacy-only in the current branch —
see section 0.

================================================================================
2. CORE RULES
================================================================================

## Physical effort

Physical effort is the primary game currency/limiter.

The preferred model is:

    STRATEGIC ACTION → REQUIRED WORKOUT → ACTION COMPLETES

Do NOT use a system where players build up a large bank of "army power" through
workouts and spend it later without exercising.

Think in terms of FULL WORKOUTS rather than individual repetitions as the main
player-facing resource interaction. Exercises may contribute to workout
difficulty/reward.

**Implementation note:** `NORMAL_TROOPS` workouts grant banked troops; `ATTACK`
with `commitAmount` spends them. Treat this as prototype until the unified
action-duration and workout-gating design lands.

## Fitness

Permanent fitness history/progress is never lost because of in-game losses.

Virtual assets can be lost:

- armies
- territories
- cities
- resources
- military positions

Fitness systems must not encourage excessive or dangerous exercise.

Rest is legitimate and should not cause permanent fitness loss or unreasonable
pressure to exercise.

**Implementation:** terminal workout sessions persist to `workout_history`;
compact history on GameState; progression coerced on load.

## Player responsiveness

Player actions should be immediate or use short presentation/animation.

Do not design core player actions around long real-world timers.

The scarce resource is the player's real-world effort, not waiting time.

**Implementation:** player commands apply immediately; **army movement** and
**construction** complete over **world ticks** when the simulation advances
(`SYNC_PLAYER_WORLD` / `ADVANCE_WORLD`). Real-time wall clock does not yet
drive that advance in production HTTP.

================================================================================
3. PLAYER
================================================================================

The player creates a custom empire.

Empire creation/customization should have minimal onboarding friction. It may be
done immediately or postponed until the player has completed one or two
workouts.

If the player loses their entire empire, the intended model is an
EXILE/COMEBACK system rather than permanent game-over. Exact mechanics remain
open.

**Implementation:** durable identity is **`playerId`** (client-supplied; Unity
default `player_local` for dev). `levelDefeat` / `TRANSITION_TO_NEXT_WORLD`
exist for authored world progression; full exile loop not implemented.

================================================================================
4. WORLD
================================================================================

The final game is a continuous 24/7 world, not a globally synchronized
turn-based game.

The world contains (product intent):

- player empire
- AI empires
- territories
- cities
- armies
- resources
- diplomacy
- world events
- fog of war
- exploration/scouting
- ongoing strategic actions

The world continues while the player is offline.

Online:
- events and interactions progress quickly
- player actions resolve quickly
- feedback should be immediate
- the experience should maximize engagement during active workout sessions

Offline:
- world activity progresses more slowly
- offline changes should be more forgiving than active-play changes
- offline catch-up should not make the player's empire unnecessarily
  vulnerable to instant destruction

Exact online/offline time scaling is not finalized.

**Implementation today:**

- State **persists** across server restart when Supabase is configured.
- **Simulation** only moves when `ADVANCE_WORLD` or `SYNC_PLAYER_WORLD` runs
  (or test/CLI harness). No background worker.
- `BALANCE.world.onlineSimulationRate` / `offlineSimulationRate` exist as
  placeholders and are **not applied**.
- **Player empire pause** (`SET_PLAYER_PAUSE`) freezes **player-facing tick**
  for invasion deadlines; other factions still simulate on advance.
- **24h protection** after workout complete and **attacker cooldowns** are
  implemented in ticks (`src/gameplay/invasion/eligibility.ts`).

================================================================================
5. PLAYER ACTIONS VS AI ACTIONS
================================================================================

Player actions are workout-gated and highly responsive (product intent).

Example:

    PLAYER ORDERS RAID
        ↓
    REQUIRED WORKOUT
        ↓
    WORKOUT COMPLETED
        ↓
    RAID RESOLVES

AI actions can be asynchronous strategic commitments.

The intended AI lifecycle is:

    OBSERVE
       ↓
    DECIDE
       ↓
    COMMIT
       ↓
    EXECUTE
       ↓
    COMPLETE / INTERRUPT
       ↓
    REASSESS

AI should not make a fresh strategic decision every global tick.

**Implementation:** `AI_DECIDE` writes `GameState.commitments`; `RESOLVE_COMMITMENT`
and `ContinuousWorldEngine` execute ATTACK, MOVE, BUILD, REINFORCE, diplomacy,
WAIT, DEFEND (posture no-op). Reassessment cadence:
`BALANCE.world.reassessmentIntervalTicks`. Commitment durations are provisional
(`BALANCE.world.commitmentDurationTicks`); movement duration uses
`BALANCE.movement` separately.

Players can respond to AI invasions via **DEFENSE** workouts while invasion
records are open (`activeInvasions`).

================================================================================
6. MAP
================================================================================

The map should have a Risk-style layout (product).

Territories must:

- have irregular shapes
- vary substantially in size and shape
- have different strategic values
- have terrain/geographic characteristics
- form an adjacency graph
- extend beyond the visible screen
- support continual expansion

**Implementation:**

- Authored **WorldDefinition** JSON: territories, polygons, adjacency, regions,
  starting owners, resource output. Instantiated into GameState via
  `worldDefinition/instantiate.ts`.
- **Unity** renders territories using `GET_WORLD_DEFINITION` + `GET_VISIBLE_WORLD`
  / `GET_GAME_STATE`; `MapProjection` for layout.
- **MapEngine** procedural hex maps remain for **legacy tests/demos** only.

The player should NOT see a uniform hex-grid appearance in the shipping product.

## Map expansion (product)

Procedural + curated themes (Iron Hills, etc.). Themes may live in Supabase long-term.

**Implementation:** multiple worlds in catalog; `TRANSITION_TO_NEXT_WORLD` when
completion rules pass.

## Fog of war (product)

Visibility: unknown, discovered, scouted, controlled; scouts reveal beyond control.

**Implementation:** **not on production GameState.** Full-world visibility for the
current authored instance. Fog types exist only on legacy `MapWorldState` /
`MapEngine`.

================================================================================
7. TERRITORIES AND CITIES
================================================================================

Cities are core strategic infrastructure (product).

Conquest destroys prior owner's city; new owner must build.

Offline defense strength scales with city level (product intent).

**Implementation:**

- **Cities** appear after **CITY** construction completes (`cities` map).
- Conquest via BattleEngine / invasion resolution updates ownership; city
  destruction rules per `applyBattle` / gameplay modules.
- **Fortification** levels, farms/mines/lumber infrastructure flags on territories.
- Construction is **timed** (world ticks); costs in `GAMEPLAY_CONFIG`.

================================================================================
8. ARMIES AND COMBAT
================================================================================

Armies are expendable virtual assets: attack, defend, move, reinforce.

Product: no normal retreat; winner eliminates losing army.

**Implementation:**

- **BattleEngine** (`src/battle/BattleEngine.ts`) is authoritative for combat math.
- **MOVE** + **strategic attack** staging: march over ticks, then battle on arrival.
- **RETREAT** exists for **AI commitments** only (reposition from non-owned tile);
  not a battle retreat mechanic.
- **Invasion** path for attacks on **player** territories: response window,
  defense workout, completion timeout, then resolve.
- Orchestrator must not duplicate battle formulas.

================================================================================
9. WORKOUT / FITNESS SYSTEM
================================================================================

Workout data → relative difficulty/effort → game effect (product).

Do not assume 1 rep = 1 soldier globally.

**Implementation:**

- Catalog + authored workouts; **GET_WORKOUT_SELECTION** for prescription.
- Session: `START_WORKOUT` … `FINALIZE_WORKOUT` (pause/resume, exercises, rest
  skip, feedback, integrity flags, abandon).
- Purposes: `NORMAL_TROOPS`, `EXTRA_CONSTRUCTION_WORKERS`, `GOLDEN_YIELD`, `DEFENSE`.
- Pipeline: fitness → PhysicalResult → GameRewardResult → apply (`rewards/`).
- Session clock: parameter `now` or injectable clock; **not** world tick.

================================================================================
10. AI WARLORDS
================================================================================

AI empires use personality, goals, memory, diplomacy, scoring, ambition.

Personality archetypes (Defensive, Aggressive, Expansionist, etc.) in balance/types.

Ambition scales persistence toward goals — see `docs/AI_COMMITMENT_AMBITION.md`.

Elimination: zero territories **and** zero armies → faction skips new AI decisions
(`isFactionEliminated`).

**Legacy sample map note:** "Celestial Theocracy" with zero territories appears in
**legacy `SampleMap` / battle tests only**, not in authored Level 1 production
worlds. Do not confuse with live `WorldCatalog` content.

================================================================================
11. IMPERIAL EVENTS
================================================================================

Famine, rebellion, crises, etc. (product).

**Implementation:** `WorldSimulator` + `runEventEngineTurn` during world advance;
`activeEvents` / `eventHistory` on GameState. Turn-based simulator adapted to
world ticks. Player choices depend on event definitions and world content — not
all event content is exercised in Level 1.

================================================================================
12. ECONOMY
================================================================================

Resources (product open): food, gold, iron, wood, stone, etc.

**Implementation (economy v1 foundations):**

- Faction `resources`; territory `resourceOutput`; **territoryEconomy** accrual
  and **COLLECT_RESOURCES**.
- **ticksPerProductionCycle** (60 ticks = one scheduled hour at 1 tick/minute).
- Food consumption cycles on world advance (`progressWorldEconomy`).
- Farms/mines/lumber as construction types + `territoryInfrastructure` occupancy.

Do not invent final balance without explicit design.

================================================================================
13. DIPLOMACY
================================================================================

Trade, peace, war, treaties (product depth open).

**Implementation:**

- `DECLARE_WAR`, `NEGOTIATE` — opinion and relationship state on snapshots.
- `OFFER_PEACE`, `TRADE` — **unsupported** in orchestrator (catalog only).
- AI may score peace/trade; commitments for those actions fail as not executable.

================================================================================
14. AUTHORITATIVE GAME STATE
================================================================================

One **GameState** for shared truth (see section 0).

Fields include: factions, territories, armies, commitments, events, constructions,
cities, economy maps, player fitness/rewards, invasions, tutorial overlay,
`worldTick`, `turn`, `lastProcessedAtMs`, pause, cooldowns.

**Not on GameState:** map polygons (WorldDefinition), `state_version` (persistence
envelope), full workout history table rows.

Engines read via `gameStateAdapters.ts`; orchestrator applies results.

**Transitional:** `WarlordState.activeCommitment` is AI runtime working copy synced
to `GameState.commitments` at handler boundaries.

================================================================================
15. GAME INTERFACE & ORCHESTRATION
================================================================================

**Product:** mobile app → orchestrator → engines → state → database.

**Implementation:**

    UNITY (or tests / HTTP client)
        ↓  POST /commands  (allowlisted commandId + parameters)
    session.ts → Orchestrator.execute
        ↓
    handlers → engines (battle, events, AI) + gameplay modules
        ↓
    GameState mutate → persist (memory or Supabase atomic commit)

The orchestrator does **not** embed AI scoring, battle math, or map generation.

Observability: `src/analytics/` (optional telemetry on commands).

16. COMMAND SYSTEM
================================================================================

**Product:** broad future command surface (empire, map, army, combat, workout,
city, economy, diplomacy, events, customization) — see prior aspirational lists
in design discussions.

**Implementation:** authoritative list is **`COMMAND_INDEX`** in
`src/orchestration/commandIndex.ts`. Summary:

`GET_WORLD_DEFINITION`, `GET_FITNESS_CATALOG`, `GET_WORKOUT_SELECTION`

COMBAT / ARMY / TERRITORY / ECONOMY / DIPLOMACY: `ATTACK`, `MOVE`, `BUILD`,
`REINFORCE`, `DECLARE_WAR`, `NEGOTIATE`, `START_CONSTRUCTION`,
`APPLY_CONSTRUCTION_ACCELERATION`, `COLLECT_RESOURCES`, `SET_PLAYER_PAUSE`

  (+ harness: `ADVANCE_WORLD` not on HTTP allowlist)

FITNESS (9): `START_WORKOUT`, `PAUSE_WORKOUT`, `RESUME_WORKOUT`,
`RECORD_EXERCISE`, `SKIP_REST`, `SUBMIT_WORKOUT_FEEDBACK`, `FINALIZE_WORKOUT`,

When adding capabilities: update `commandIndex.ts`, handlers, tests, allowlist if

================================================================================
18. COMMAND / RESPONSE MODEL
================================================================================

Request: `commandId`, `playerId`, `parameters`, optional `requestId`, `timestamp`.

Response: `success`, `stateChanges`, `events`, `notifications`, `payload`, errors,
resource/territory/army change arrays.

Mutations do **not** include full `gameState` in `payload` — call `GET_GAME_STATE`.

Standard errors: `INVALID_COMMAND`, `MISSING_PARAMETER`, `INVALID_TARGET`,
`INSUFFICIENT_RESOURCES`, `INSUFFICIENT_TROOPS`, `ACTION_NOT_ALLOWED`,
`ENGINE_UNAVAILABLE`, `ENGINE_ERROR`, `TIME_UNAUTHORIZED`, `WORKOUT_SESSION_INVALID`,
`FEATURE_NOT_IMPLEMENTED`, `PERSISTENCE_FAILED` (HTTP layer), etc.

================================================================================
21. PERSISTENCE
================================================================================

**Supabase (implemented):**

- `player_worlds`: JSON payload + `state_version` (CAS).
- `workout_history`: per `(player_id, session_id)`.
- `gameplay_telemetry`: schema/mappers; append-oriented, not required for play loop.
- Service role server-side only; never Unity, never commit secrets.

**In-memory:** dev fallback.

Hydration: `migrateGameStatePayload` on load; rebind authored geometry from catalog.

Do not `db reset` linked production projects.

26. AI AGENT RULES
================================================================================

Before modifying Rep Wars:

1. Read this file and section 0.
2. Inspect relevant code (`commandIndex.ts`, handlers, GameState).
3. Reuse engines; do not duplicate battle/AI/event math.
4. Preserve authoritative GameState and CAS persistence semantics.
5. Unity: presentation only unless fixing a client/API defect.
6. Update `commandIndex.ts` + tests + FRONTEND_API_CONTRACT when changing commands.
7. Do not push Supabase migrations or reset remote DB without explicit user request.
8. Do not print secrets (`.env`, service role keys).
9. If product doc conflicts with code, report the discrepancy; prefer code for
   current behavior unless tasked to align code to product.
10. Do not invent unfinished rules or tick durations without design sign-off.
